0. 已确认的平台使用方式

人类提出想法与需求 → agent 选材、制作和适配 → 组件组合与布局配置 → 检查与预览 → 修改 → 批量生成 → 保存、导出 → 统一接入游戏角色系统。

- 自动检查覆盖资源与版本、空间尺度、合法摆放、连接与通路、使用点及兼容性。实际画面和动作合理性仍须在游戏中观看，程序检查不能代替观感验收。

- 交付包含可编辑源、制作流程、最终布局、设施配置、资源版本及完整依赖，支持关闭重开、继续修改和重新生成。
- 平台验收沿这条完整链进行：agent 能按同一流程制作新的合规布局并接入游戏，不以只能切换几个预制样板代替制作能力。

3. 你的建设范围

3.1 公司空间组织

初期采用“单层、多区域、可组合布局”，先支持直播区、工作区、休息区等不同用途。公司内部采用连通空间分区：一份布局包含开放区域、封闭房间以及墙、门口、通道和连接关系，角色沿实际可通行路线往来；镜头可总览或查看局部。

统一层级为“公司 → 楼层 → 房间 → 工位 → 工位内部部件”。沿既有合同为各层级建立稳定身份与明确归属，区分资源模板和场景实例；名称、外观或观看位置变化不能随意改变实例身份。工位复用组合设施能力，使用点仍属于实际设施。房间可含不属于工位的家具和装饰，楼层可含公共区域及其设施，不强迫所有物件归属工位。区域不一定有墙；用途、建筑结构与家具配置分别管理，直播、工作、休息是首批用途，不写死为固定三区模板。首包仍仅验证单层代表房间，两种配置的出口不变。

当前平台目标是 agent 能制作任意符合已定义规范的公司布局。规范明确空间尺度、连接、摆放、资源和交互边界，新布局由同一运行链加载、检查和使用。玩家是否能自由拆墙、装修、搬家具属于后续产品选择；制作端能力与玩家端开放的操作权限分别决定，本阶段不据此建设玩家装修系统。

“符合规范”的实际支持范围由后续“布局规范与摆放检查”工作包落实为 agent 可生成、可校验的明确规则。本次记录以下待确定项，不预先声称已有通用支持：
- 墙体允许的形状、转角、门洞及连接表达方式；哪些形状首版支持，哪些暂不支持。
- 设施允许的旋转轴、角度范围或离散角度，以及禁止缩放或允许的缩放方式、范围和适配限制；不能默认任意缩放后仍可使用。
- 公司空间、区域、墙体及门口的尺寸范围；当前代表房间的单个尺寸不是已验证的可用范围。
- 通路、门口、接近区、实际使用区及离开空间的留量和可达性要求，并与现有角色移动、转向和接触能力对应。
- 不支持情况及具体拒绝原因，包括未声明或未验证的形状、变换、尺寸和连接方式；楼层、楼梯等既有边界继续保留。
上述技术参数由副总工与总工依据现有实现，在恢复实施后以该包代表布局验证并确定，写入相应规范及校验入口，不要求用户决定技术数值。未知支持范围不能以“任意符合规范”概括为已实现能力。

空间内容包括地板、墙、门窗或通道、边界和区域连接、空间材质、灯光及必要观看镜头。模块化尺寸与接口要能复用，不把每个房间制作成无法修改的一整块模型。门口和通道必须在导航中真实连通，不能只有视觉上的连接。

多房间观看由后续“场景观看与可视性”工作包补齐：明确公司总览与局部查看方式，以及墙壁或屋顶遮挡室内人物时的处理。复用现有镜头和渲染能力，选择足够解决代表场景遮挡的简单剖切、隐藏或透明方案；本次不预选复杂摄影方案。观看处理只改变渲染可见性，不能改变真实碰撞、导航、设施占用或可用性。具体方案与切换规则留待恢复实施后核实，不扩展为摄影系统或装修编辑器。

3.2 四类基础设施

类型 | 代表样件 | 需要证明的机制
静态装饰 | 绿植、挂画 | 地面、墙面或桌面摆放，替换、材质配置及资源加载与释放。
简单动态物件 | 补光灯、屏幕 | 状态驱动实际灯光、显示内容或简单动画；状态切换和保存恢复正确。
单人交互设施 | 椅子、单人直播工位 | 接近、对齐、使用、离开；预约、占用、同位置争用拒绝及取消清理。
多使用点设施 | 双人沙发 | 各位置具有独立使用目标、预约、占用与释放；两个位置可分别使用，同位置争用拒绝，一个位置释放不影响另一个。

按机制选择少量代表样件，验证制作、游戏运行和保存恢复，再复用机制扩展内容，不为每个名词批量生产美术款式。单椅通过不能推定双人沙发通过，静态灯具加载成功也不能代表灯光状态切换通过。

3.3 组合设施与直播工位

组合设施是正式的生产、摆放、复用和交付单位；组合关系与上述四类用途分别管理。同一个组合可以包含装饰、状态设备和角色使用位置，部件保留独立身份与可调整、可替换能力。

首批直播工位的组成约定：
整套直播工位
├─ 桌子
│  ├─ 显示器
│  ├─ 键盘
│  └─ 桌面麦克风
├─ 椅子
└─ 补光系统
   ├─ 灯具与支架
   └─ 灯光配置

- 移动或旋转整套工位时，所有部件及实际灯光一起变化，保持组合内的相对关系。单独移动桌子时，桌面设备随桌子移动，椅子和补光系统保持各自位置；调整某个部件时，仅改变该部件相对父级的配置。
- 桌子提供可配置的桌面承载面和安装位置；设备记录依附对象、安装位置、相对位置及朝向。首次适配由 agent 完成，移动、旋转、复制和重新加载自动保持关系，无需用户反复人工对齐。更换不同尺寸的桌子时，agent 根据新承载面重新适配并检查，不把沿用旧偏移视为自动适配通过。
- 补光系统支持多灯组合，保存灯具与支架资源、启用状态、位置、照射方向、亮度和色温。它随整套工位移动、旋转，也能独立调整。灯光配置须驱动实际渲染光照，预览检查补光效果与角色面部受光，不能只显示灯具模型或保存未生效参数。多工位的实时灯光、阴影与可见区域预算沿第6节对应工作包确定，复制工位不能无上限增加高成本灯光。
- 组合可以保存为带版本的模板，生成多套互不影响的实例。普通部件外观替换遵守固定功能规格，不改变使用位置、碰撞、导航、容量与状态语义；确需改变功能规格时另走显式配置变更和兼容检查，不能伪装成换外观。角色控制器继续共用。已保存实例绑定具体模板与资源版本，模板更新不自动改变既有公司；显式升级与局部调整保留规则在第7节细化。
- 某部件正在被角色预约或使用时，影响它的组合移动、拆除或替换先明确拒绝，沿既有取消与实际离位规则清理，不带着角色瞬移。
- 保存完整组合关系、部件与资源版本、实际相对配置和设备状态；关闭重开后保持布局与对齐。依赖不全或变更失败保留原组合，不能提交半套工位。

组合设施验收包括整套制作、整体移动与旋转、桌面设备跟随、局部调整与替换、多实例独立、实际灯光变化及保存恢复。多使用点的独立占用仍须单独验证，不能用组合树存在代替交互机制通过。

3.4 共用平台机制与制作入口

平台机制：素材生产与导入、配置布局、合法摆放/替换/卸除、导航与使用点、状态及占用、保存恢复、版本与依赖移交、按需加载和释放。普通新设施与第二套布局应主要走资源和配置，而不是反复改人物控制器。

以 agent 为主要制作者：优先可重复脚本、结构化数据、错误定位和独立输出。人类只需打开预览、切换方案、执行代表操作并判断效果；本阶段不建设庞大的拖拽装修编辑器或通用编排框架。

4. 与角色平台共同确定的接口

职责边界：副总工提供设施的位置、接近点、使用点、接触面、朝向、离开点及使用状态，负责空间、设施、组合关系与布局数据。总工的角色系统负责人物移动、坐起、姿态与身体适配，并负责共享运行模块集成和最终联调。设施使用状态沿用共用预约/占用事实与角色实际执行反馈，不另建一套与现有座位状态冲突的占用记录。

接口缺口按以下方式处理，具体文件边界已在首次正式握手中确认：
- 空间、设施定义、组合或布局适配的问题由副总工修改；人物移动、动作、姿态、身体适配及角色状态机问题由总工修改。副总工提交具体输入、预期行为、实际失败、复现步骤和源码版本，由总工处理角色接口缺口；不能复制角色逻辑绕开问题。

测量所用布局的加载字节、几何/材质/贴图、draw calls、帧耗时和释放情况，区分静态空间与角色/动态开销。RTX4090开发机与限速模拟不能冒称普通电脑实测；普通设备缺口保留，继续独立任务。在线人数不等于房间同屏人数，先按单角色/双实例验证。

“补光系统与场景性能”工作包在既定多工位代表场景中确定实时灯光和阴影预算，明确可见区域与区域外灯光的启用、简化及恢复规则，避免复制工位时无上限增加高成本灯光。实时灯数量/影响范围、哪些灯投射阴影及阴影成本、可见区域的判定与处理方式、超预算时的简化方式均为本次待确定项；恢复实施后依据实际渲染结果与成本验证，由两位负责人确定。记录场景与工位配置、设备/浏览器、镜头和测量条件、实际受光效果与适用范围，不为此新增庞大测试矩阵，也不以开发机结果证明普通电脑达标。简化策略必须如实记录，不能把未实际作用于角色的灯光参数算作补光通过。

7. 保存与业务边界

保存最终布局、设施实例及资源版本，不能只保存随机种子或脚本路径。缺失资源、错误版本或非法布局返回具体错误并保留原场景。明确升级/迁移/回退，资源ID不随意复用。重开时基于有效角色和任务恢复占用，不盲目复原旧锁。

组合模板升级沿既有身份、版本与失败恢复机制落实：已保存布局绑定明确的模板及部件资源版本，更新模板默认不改变既有公司。显式升级前逐项核对部件身份/替换关系、相对位置与安装依附、设备状态，以及用户或 agent 已保存的局部调整，明确哪些可以保留、哪些需要适配或因不兼容拒绝；不能默默抹除局部调整。具体匹配规则、可保留字段和不兼容条件列为恢复实施后该子包的待确定项，由两位负责人依据实际模板变体验证。升级失败须返回涉及的部件、字段或依赖及具体原因，并保留原组合、原版本和局部配置；不得只更新半套。用户局部调整在此仅指已保存数据的来源，不因此开放玩家装修玩法。以同一组合代表样件覆盖可保留调整的升级、不兼容保旧与关闭重开，不另建通用模板管理平台。

多楼层存档保存公司规模、完整楼层列表、房间用途与布局、公共区域、设施及工位实例、父子关系、最终变换、模板和资源版本以及已保存设备状态，不能只保存当前可见楼层。关闭重开后各楼层与房间均可恢复；切层往返配置一致，同名房间和同款工位不串用身份、位置或占用记录。占用恢复仍按有效角色与任务核对，不能盲恢复旧锁；缺资源、错误版本或非法归属返回具体原因并保留原有效场景或存档。模板升级复用前述版本绑定、显式升级、局部调整保留与失败保旧规则，不另建第二套机制。

布局存档不是完整公司经营存档。后续公司等级、解锁、收益、招聘和PK由业务系统决定；这里只提供已验证的展示/使用接口及必要标签。未来头像/招聘页仍沿总工角色身份和最终外观记录，不另建人物数据。

8. 并行协作、验收与持续工作

效率与验收尺度：每包聚焦证明一种必要机制，以最少代表样件完成制作、运行和受影响检查。第二个标准输入能复用同一流程，优先于多制作几个精美房间。严重技术错误、错误占用及保存丢失必须处理；装饰细节和大量风格款式留待后续扩充。不能因美术细节无限延长当前包，也不能以暂缓美术扩充为由降低动作合理性、状态正确性或数据恢复标准。

日常可逆技术选择自主实施；费用、授权缺失、重大画风/产品范围及无法独立解决的阻碍集中提出具体选项。可以派发边界清楚的制作/实现/审查；每次明确记录任务难度、模型、思考深度及理由，并使用真实工具参数。禁止默认继承配置冒充明确选择。

按隔离目录/工作树分工。总工协调共享运行模块集成，普通功能检查协调后可并行，只有可比较性能采样、重型录制或重导出安排必要窗口；不要关闭他人服务或静默替换公开入口，不额外长期占用端口。优先新增独立场景模块/数据，main.js必要接缝由双方约定的窗口合入。
