# 参数驱动角色生产契约

本文件定义“同一套参数可以重复生产并批量进入游戏”的工程接缝。它是流程契约，不是能力清单；当前能力事实仍只看 `docs/CAPABILITIES.md`。

## 一条生产记录

可编辑源和发布派生体分开留存。若原身体内嵌的衣面已有完整的同源独立装备，按配方核对原始图元、骨架、绑定和贴图归属后，可在发布体省去对应重复数据。生产工具须给派生身体和装备目录登记独立摘要；共享同一 GLB 的多个身体各自保留 fit。旧角色记录继续指向旧身体。制服样件一键核验为 `python -B scripts/production/build_source_outfit_release.py --check`。[配方与重新生成](../evidence/m2-source-outfit-release-v1/body/README.md)

每个候选都从不可变的 `template.sha256` 和一条显式 `recipe` 开始。recipe 至少包含参数组类型、参数键、单位/类型、已观察的允许值、导出设置、目标基模和资源版本。执行器必须在每次打开源文件后重新发现组 ID，设置参数，冷开回读非目标字段，并记录：

- `recipeSha256`：最终参数及导出设置的身份；
- `sourceExportSha256`：原生导出的 VRM 身份；
- `bodySha256`：进入游戏的完整身体身份；
- `fit`、coverage、装备和附件的精确版本；
- 工具版本、许可、失败原因和恢复快照。

同一个 recipe 重跑可以复用已经核对的字节包；`.vroid` 容器本身不承诺跨运行字节相同。不同 recipe 必须产生不同身份，不能覆盖旧资源。

## 资源拆分粒度

资源按“是否能独立替换、适配、保存和验证”拆分，不能按网格零件数量任意拆碎。每个可装备对象都必须有自己的 `styleId`、适用 `bodyType`/体型范围、版本、来源和 fit；对象内部可以包含多个网格、骨骼组和材质。

- **基础人体包**：完整身体、骨架、蒙皮、表情和基础材质作为一个不可分割的身体身份。四肢、躯干和头部不能在运行时随意拼接成不同人体。
- **脸型与五官**：脸型使用作用于同一头部网格的参数/形态配方；眉、眼、鼻、嘴、耳可以有独立参数域，但必须声明眼睑、眼球、牙齿、口腔、表情和发际等受影响检查。五官不是任意零件拼装。
- **发型**：对外是一个完整可装备的发型包；内部可分刘海、头顶、侧发、后发、马尾和动态骨骼。内部网格由同一 manifest 原子加载和卸载，不能出现只换后发而遗留旧刘海的半套状态。
- **服装**：以完整款式/版型为生产单位，例如一件上衣、一条裙子或一条短裤。只有实际需要叠穿、互斥、独立动态或独立覆盖时，才拆成外套、内搭等多个装备槽；领子、袖子和衣身通常属于同一件服装内部结构。
- **鞋袜、饰品和手持物**：按可独立装备的物件拆分。麦克风等功能道具还必须携带握持点、手型、使用端目标和动作限制，不能只保存骨骼挂点。

Agent 可以在制作阶段编辑内部网格和骨骼组，但交付给运行时的是完整装备包及其适配数据。新增一个普通款式不得修改通用动作控制器；如果必须单件修正，应保存为该装备的 fit/覆盖/动态配置。

资源包的最小目录约定为：`source/`（可编辑源与许可）、`recipe.json`（参数）、`manifest.json`（运行资源闭包）、`fit/`（身体/动作/接触适配）、`coverage/`（身体遮挡恢复）、`dynamic/`（附加骨骼或动态）和 `provenance.json`（工具、版本、输入输出身份）。

## 可替换角色底座

角色底座固定以下运行时约定，后续 Agent 只替换通过合同的资源，不为每件素材复制一套控制器：

1. **骨架与动作层**：男女基模可以使用不同网格和身体比例，但必须映射到同一套语义骨架、单位、参考姿势、左右定义和动作接口。站立、走跑、转向、坐下、起身、讲话和舞蹈由共用行为入口驱动；身体差异放在重定向、步幅、脚底、骨盆和座位适配配置中。
2. **身体层**：每个 `bodyType` 是完整身体、骨架、蒙皮、表情和基础材质的不可变身份。身高、胖瘦、脸型或局部比例变化生成新的派生 body 身份，不能只在运行时整体缩放后复用旧服装和接触数据。
3. **外观层**：脸型/五官使用参数配方，发型使用完整 style 包，衣服/鞋袜使用完整款式包，饰品和持物使用独立附件包。它们都通过槽位、互斥、覆盖和版本规则组合，角色记录保存最终资源身份而不是只保存随机种子。
4. **适配层**：身体与资源之间保存精确 `fit`、`coverage`、`dynamic` 和动作限制。几何、头围、腰胯、鞋底或材质变化触发对应适配；无关资源可复用。新资源没有精确 fit 时必须拒绝或明确回退，不能因为骨骼名字相同就自动通过。

## 反向验收闭环

每种新资源都按最终游戏路径回归：

```text
统一参数/款式请求
→ 美术源与导出资源
→ 身体/服装/发型/附件 fit 与 coverage
→ manifest/catalog 登记
→ 角色记录创建
→ 房间加载与动作/换装/接触
→ 关闭重开恢复
→ 失败组合拒绝并保留旧造型
```

只有这条链在男女代表基模上都跑通，才能把“替换资源即可正常表现”作为该类资源的生产规则。单一模型的漂亮截图、静态蒙皮检查或只替换贴图都不能证明底座完成。

## 分层流水线

1. **Authoring**：原生工具按 recipe 生成 `.vroid` 与 VRM，失败只影响该条。
2. **冷开与差分**：`native_dependency_delta.py` 比较真实顶点、morph、骨骼/IBM、材质、图片、动态和扩展，输出 `inputs-unchanged` 或 `needs-recheck`。
3. **资源包**：`native_body_package.py` 生成完整身体、独立装备和覆盖数据。它只证明来源和绑定数据一致，不自动授予动作、表情或附件 fit。
4. **适配分流**：`native_batch_gate.py` 根据差分为每条生成适配任务。未变化的检查可复用；变化的脸、头发、握姿、材质、动态、接触必须进入对应 adapter。禁止按人物名称、性别或新 SHA 猜测继承。
5. **共用登记**：全部输入通过身份核对后，注册器原子写入资源目录和 catalog；冲突、缺件和半成品拒绝发布。
6. **角色记录**：`native_record_batch.py` 只为已有精确 body/fit 生成稳定记录请求。记录创建、关闭恢复、双实例隔离是独立证据。
7. **游戏准入**：运行时和视觉检查通过后才可标记可用。单张截图、源工具截图、CPU 绑定检查或平均 FPS 都不能替代这一步。

## 适配和准入的证据

适配器接收身体、装备、材质及源配方的精确版本，逐项声明已核对的依赖。身体包和遮罩检查覆盖文件闭包、身体与装备摘要及透明度。表情、发丝、头部附件及目标设备性能各有独立证据。脸部 primitive、morph、UV 或骨架结构改变时，按实际变化选择复核项目。

生产与验收状态以 [能力清单](CAPABILITIES.md) 为准。历史门报告可按路径复算，当前工作包与固定构建见 [恢复入口](CURRENT-FOUNDATION.md)。

## 批量生产的完成条件

一批任务可以同时运行，但每条必须能独立重试、独立拒绝、独立登记和独立回滚。只有当每条的适配任务均有精确输入/输出身份，公共运行链完成记录回读与关闭恢复，且所列设备上的正常速度检查通过，才将该条加入可用资源库。未通过条目保留诊断包，不阻塞已通过兄弟项，也不被标签改名为通过。

## 创建角色与修改已有角色

- 新建角色时，`native_record_batch.py --readiness-report <gate.json>` 只给该报告中正式准入的精确身体生成请求。审查中的身体可以用诊断模式运行并保存拒绝原因。
- 给已有角色应用同一配方时，`character-production-batch-edit-v1` 携带 1–4 份最终记录与共用修改。逐一检查身体兼容性并保留身份。整批成功才写出新的记录数组；任一条失败时报告条目索引、身份和原因，原记录继续可用。输入输出与命令见 [制作 CLI](PRODUCTION-FLOW-CLI.md)。
- 作者制作的同款唇妆可以根据肤色选择不同底图。源文件、身体版本、实际采用的适配版本和资源摘要要能从最终记录追溯。游戏包从记录选取所需资源，换机器后仍可核对文件并恢复人物。两个女性样件的完整实例见 `evidence/m2-native-lip-game-handoff-v1`。

## 发布资源旁车边界

当静态预算显示需要压缩时，压缩产物必须是绑定到具体 `sourceModelSha256`、覆盖清单、原图 SHA、材质/UV/采样器、alpha 合同和解码器版本的独立旁车。`scripts/m2-ktx-pilot-v1/prepare-facecontour-sidecar.py` 已为当前两份 FaceContour 身体生成 Body map KTX2 候选；它保留原 VRM 与 PNG/Canvas 回退，不替换 VRM 内嵌图，也不自动修改运行时材质。旁车的确定性、KTX 校验和源合同属于生产证据，不能清除 `surfaceAndTexture` 或 `runtimeRecordAndBudget`。只有另行完成精确 loader 身份、颜色/透明/采样器、染色路径、释放生命周期、浏览器动作和目标设备证据后，才可写入 `native-budget-admission-v1`。

批产入口的失败语义同样属于契约：runtime 证据缺少 record SHA、body SHA 不匹配、accepted gate 与 catalog 身份不一致、重复 body 类型或部分记录写入失败时，必须拒绝并保留诊断；本轮新增的回滚清理只清除本轮新输出，不覆盖既有证据。`technical-candidate` 与 `runtime-admitted` 在请求批次中显式区分。

## 统一参数到批量角色请求

美术 Agent 的输出先落为资源矩阵行，再由 `scripts/production/variant_batch.py` 生成角色请求。最小组合键是 `bodyType + styleId + variantVersion`，请求还必须带稳定 `stableId`。同一身体和款式可以存在多个明确版本，版本缺失、重复或请求版本不匹配都会拒绝。矩阵行保存身体 SHA、参数配方 SHA、资源/fit/coverage 引用及对应哈希，候选行可以进入审查和预览，正式生产要求匹配已审核的款式版本、身体与完整穿搭。显式诊断模式可以生成候选请求，单独保存在 `diagnostic-requests/`。

概念图或美术预览先使用 `scripts/production/look_spec.py` 的 `zbgs-avatar-look-spec-v1` 作为输入边界。它要求明确身体变体、脸型、发型、颜色、装备角色、附件挂点和来源模式。`concept-reference` 只表示待制作的参考请求，`structured-asset` 必须携带精确身体 SHA、源配方与资源清单哈希；它不会从图片推断网格、权重或服装版型。规划结果会对每个装备按精确 `bodyType + styleId + variantVersion` 查表，并核对结构化资源的身体 SHA，缺失、错配或未准入时逐项拒绝，避免把“看起来相似”的概念图直接当成可运行角色。

当前输入格式只携带一份装备清单哈希。同一文件中的多个条目可组成套装；跨文件组合、任一件身体或配方哈希错配会拒绝整套。命令行同时复算装备清单文件哈希。脸、发、各颜色和附件的待核项逐域返回，装备全部匹配时整套仍保留候选身份。可用 `evidence/m2-look-intake-v3` 对照两份真实输入。

共用穿搭请求只填写一次 `styleId + variantVersion + outfitRole`，每个主播保留自己的身份和身体。平台展开该身体整套装备的槽位、资源 ID 和 SHA，游戏制作端再次匹配完整集合。代表矩阵现含十行；固定构建 7809b98bd700 上，男女两个既有基模生成并恢复了裤袜造型，缺少同款适配的原生男体被单独拒绝。正式放行数量和证据以 CAPABILITIES 为准。

原生虹膜款式的重复生产输入见 scripts/production/native-facecontour-iris-batch-v1.json。每个身体条目提供身体与包来源的精确版本；native_palette_compatibility.py --stage、--publish、--check-published 依次生成、发布并回读。检查实际虹膜 UV、材质、图片及同图其他消费者后才复用作者款式。登记表随匹配结果生成，原色记录仍按原配方恢复。正式资源适用的许可与运行预算必须单独满足。
