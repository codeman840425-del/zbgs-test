建议采用的顺序

先完成当前按需加载交付，再验证HTTP内容编码与不可变缓存，然后用一组代表贴图验证KTX2及改色兼容，最后决定是否加入网格或动画编码。每一层单独记录收益，收益不足就结束该层试验。当前证据支持采用现成编码器与Three加载器，尚无本项目压缩前后实测结果。

源文件和编辑规范继续作为制作依据，压缩文件作为带独立SHA和配置版本的游戏发布派生物。优先维持几何、骨架、形态键及VRM数据，避免把资产优化变成新一轮人物修模。

四个实际平台如何处理资源

检索未发现可完整核对且与本项目同栈、同换装合同的商业经营游戏流水线。以下采用实际开源浏览器世界和avatar平台，分别记录相似处、已证实实现及适用边界。源码均固定到本次访问时的提交。

Webaverse

MML 3D Web Experience

实际可运行的浏览器多人世界与avatar editor，Three.js，MIT。提交b3fed99f3bae267a23c66e195794ac22e2b81107，所读子包声明Three 0.182.0。GLTFLoadingWorker使用glTF Transform WebIO、Draco和Meshopt编解码依赖，在Worker内下载与处理模型，按maxTextureSize缩小普通图片，再写出处理后的GLB。它跳过KTX/KTX2/Basis图片处理，因为该路径不能直接用createImageBitmap读取这些压缩图片。

Hyperfy

Three.js及three-vrm浏览器虚拟世界。当前开源提交5d20037435a1d86cda088382bb12737e9f18d5f6，GPL-3.0。ClientLoader注册VRMLoaderPlugin并缓存请求/结果。服务端注册@fastify/compress，对哈希资源设置一年public immutable缓存，对入口HTML设置no-cache/no-store。该处能核实HTTP处理与内容寻址。

环节处理方式及实际意义本项目的选择
制作源→游戏导出保留可编辑.blend、原图、骨架、动画源；离线生成游戏版本和版本化配置。按部位与材质选择贴图大小/格式，共享经验证资源。继续既有源→导出闭环。增加发布派生层即可，源与运行资源的关联进入manifest。
传输与CDNHTTP gzip/Brotli会减少线路传输字节。浏览器解码后GLB字节恢复，fetch.arrayBuffer()通常拿到解码后的内容。压缩PNG/JPEG/WebM已较紧凑，应按收益选Content-Type与大小阈值。先试已固定GLB、动作/配方JSON和JS。正确协商Accept-Encoding、Content-Encoding、Vary；缓存哈希资源，入口/索引可更新。避免把.glb.br当普通GLB下载后直接解析。
网格/动画编码Meshopt可编码bufferView，覆盖顶点、索引及动画数据，编码之外的量化、重排、重采样各有损失或身份影响。Draco主要处理网格几何，不能概括成全部动画压缩。优先一个无VRM扩展的服装派生试验，再考虑动作。比较解码后实际数组，先禁用额外简化/量化/合并。
图像文件→GPU纹理PNG/WebP主要减少图像文件字节，GPU常仍使用解码纹理。KTX2/Basis按设备转成支持的GPU压缩格式，GPU驻留可能下降。分辨率减半，两维面积约四分之一，质量由近景用途决定。先选择一张有代表性的贴图，并按alpha/颜色/法线数据选择编码。测实际GPU格式与mip大小。需要Canvas读像素的材质先保留兼容路径。
音视频按播放需求选已编码的MP4/WebM及AAC/Opus等，长视频可用HTTP Range/流媒体与延迟加载。重新套gzip通常收益有限。把游戏实际音视频和验收录像分开统计。视频转动作产物是骨骼/曲线数据，按动画数据处理，勿为压缩重新跑真人识别。
分包与释放只取当前身体、装备和动作，共享可复用资源，处理取消、失败与缓存释放。减少请求不自动减少场景已持有的GPU资源。已有按需装备加载沿当前工作继续，报告保留限定范围。不要为压缩试验另建全库预载或通用LRU。

当前版本的兼容性与数据身份

  • 本机Three r187 GLTFLoader包含EXT_meshopt_compression和KHR_meshopt_compression，并提供setMeshoptDecoder、setKTX2Loader和setDRACOLoader。KTX2Loader需要detectSupport(renderer)，转码器JS/WASM与加载器应锁在同一Three发布版本并自托管。浏览器WASM、Worker、CSP、跨域/MIME及文件路径需在实际部署验证。低能力设备可能转为非压缩RGBA，必须记录实际结果。
  • three-vrm 3.5.5通过GLTFLoader插件加载。核心加载器支持格式尚不能证明VRM旧扩展/MToon、VRMC_vrm及VRMC_materials_mtoon全部在新产物上正确。按真实输入扩展清单保留人物、表达、lookAt、spring bone、约束和材质引用。旧VRM的materialProperties等数据可能直接持有texture/node索引，改写索引必须同时更新引用。
  • 当前character-appearance.js的neutralTexture会读取texture.image，drawImage到Canvas后getImageData，再生成灰度可染色贴图。KTX2的压缩数据无法直接沿这条Canvas路径当HTML图像使用。最小试验先保留该类动态读图输入，或离线生成可染色底图/遮罩并以原材质语义接入。若改色最终产生CanvasTexture，其GPU驻留仍要计入，不能只报原KTX2节省。
  • gltfpack官方说明默认会重排/量化网格、合并mesh、重采样动画和裁剪节点，且丢弃不支持的自定义扩展。直接用默认命令处理整个人体VRM会危及扩展和下游索引。-kn/-km/-ke/-noq各自只能保护部分行为，不能推出全部VRM与顶点身份保持。
  • glTF Transform注册ALL_EXTENSIONS指该工具所提供的扩展实现集合。读入器对缺失required扩展报错，对缺失optional扩展报警，不能依赖它无损保留未知VRM数据。通用CLI optimize不应直接覆盖人体。若后续采用，先选择无VRM服装或实现受控扩展保留/引用更新，再核对写出文件。
  • HTTP内容编码还原后，资产解码字节SHA可继续与原GLB一致。重新封装KTX2/Meshopt/Draco时，文件SHA必变，即使几何数值相同。发布manifest须记录sourceSha、runtimeSha、工具与配置版本、依赖闭包。服装fit须引用实际运行资源身份，原fit不能简单改白名单冒充适配。
  • 进一步量化或重排可能改变POSITION/NORMAL、JOINTS/WEIGHTS、索引、morph target顺序与几何身份。当前按顶点索引执行的改脸、身体/衣层mask、shape-fit和源对照都须保持映射或生成精确新版本。若首轮只做纹理派生，几何/骨架/形态键数组应保持不变，差异即可定位。
  • 解码器不可用、转码失败或派生身份错误时，依据manifest明确选择已验原资源并记录fallback，或保留当前人物并返回结构化失败。原资源与派生资源各有SHA，切换要沿已有prepare/commit语义，避免隐式替换造成记录与外观不一致。

步骤最少输入与执行退出和记录
A 传输层固定一男一女当前清单；复用其现有身体和默认装备，再取一份实际动作/配方数据。分别测identity/gzip/Brotli相同响应。若Brotli依赖当前不具备，先完成gzip。核Content-Encoding/Vary/Content-Type、解码后SHA、实际网络encodedBodySize/decodedBodySize/transferSize，冷/暖缓存各记录。原字节一致时复用原动作证据，只核正常加载与失败恢复。无明显收益的文件跳过压缩。
B 贴图层从同一男女基础中各选代表颜色/alpha贴图，保留同分辨率，先UASTC一个配置。核MToon主色/阴影色及眼口alpha。需要Canvas改色的输入先留原，或单独做离线可染色底图方案。首轮只一个质量配置。如有明显画质问题，最多增加一个有原因的候选或保原该贴图。记录输入/输出依赖清单、转码时长、实际format/mip字节、额外Canvas副本。通过一个身体再补另一性别受影响对照。
C 网格与动画，按A/B结果决定复用一件真实连体服或短裤，选择无VRM扩展的独立GLB，先测试无额外量化的Meshopt编码。若动作数据占比仍显著，再对一条实际走/跑或说话动作试验。核解码后数组和引用，若发生重排或量化先报告真实差异与影响，保留原路径。Draco仅在网格传输仍是瓶颈且Meshopt方案不足时作一个对照。冻结女裙和30秒舞不改。
D 最小运行核查仅对新派生影响的男女、服装及动作，复用已有预览场景和正常速QA。改脸使用现有嘴宽/复位和一个现有表情序列，换装与记录恢复沿原入口。观察眨眼/口型/注视、alpha边缘、阴影、法线、接缝与改色。走跑转坐起复用既有链。相同镜头/光照并排近景及游戏距离观看。未改变几何的方案不重开艺术精修。
E 一次决策一份表汇总收益、兼容问题、回退和生产命令。只有新发布字节变化才补相关检查。收益稳定且不引入当前必需能力退化就形成可重用发布步骤。无收益/兼容代价高则保原并结束试验，转回其余M2能力。

测量字段

  • 文件与网络同时记assetBytes、全部外部依赖bytes、编码器/解码器JS/WASM首次下载、实际HTTP encodedBodySize与decodedBodySize。transferSize含协议开销且缓存命中可能为0，跨域Resource Timing需要Timing-Allow-Origin。
  • 将下载、通用解压、GLTF解析、Meshopt解码或KTX2转码、首帧准备、首次换装分开计时。浏览器合并阶段时如实记录整体parse区间，不能编造细分。使用同一固定版本、设备与浏览器，冷加载至少3次取中位数，暖缓存一次确认即可。
  • GPU记录texture.format、colorSpace、尺寸、mip层和字节估算，以及Canvas/原图CPU副本。renderer.info.memory.textures是数量，不能直接当显存字节。无可靠GPU驻留API时明确估算方法，不把传输文件大小填成显存。
  • 纯计算示例，单张2048² RGBA8含完整mip约21.33MiB；4×4/16byte块压缩含mip约5.33MiB，4×4/8byte约2.67MiB。由尺寸和格式公式得出，末级块取整会有差异，数值不是本项目压缩结果。GPU格式回退RGBA时相应节省可能消失。
  • 同一画面正常1×动作和近景对照负责视觉判断，技术数组/引用校验负责数据兼容。开发机数据只覆盖开发机，普通电脑缺口继续保留。
